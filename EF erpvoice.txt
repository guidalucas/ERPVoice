1. Qué es y qué resuelve

ERPVoice es un MVP voice-first para stock y cuentas corrientes. Convierte audio o texto en acciones de negocio, las confirma en una interfaz tipo WhatsApp y persiste el estado en una base local. El objetivo no es ser un ERP completo, sino un prototipo operativo para probar captura de voz, interpretación con IA y escritura en persistencia local.

2. Stack real

Frontend: React 18, TypeScript, Vite y Tailwind CSS.
Backend: Node.js, Express, dotenv y sql.js.
IA: Groq para chat completions con Llama y para transcripción con Whisper.
Persistencia: archivo SQLite local en `server/data/erpvoice.sqlite`.
Túnel: ngrok para exponer el backend local cuando se integra con Meta WhatsApp Cloud API.

3. Arquitectura general

Hay dos superficies principales:

UI local: el usuario escribe o graba un comando en el simulador de WhatsApp flotante. El sistema transcribe, interpreta, propone acciones y espera confirmación.
Integración Meta: el backend recibe webhooks de WhatsApp Cloud API, procesa texto o audio, guarda el evento y responde al emisor.

La UI y el backend comparten el mismo modelo de negocio, pero no comparten una única librería de parsing. El frontend usa `voiceModelService.ts`, `voiceParserService.ts` y `transactionService.ts`. El backend usa `metaWebhookProcessor.js` y `database.js`.

4. Flujo del frontend

El simulador vive en `src/components/split/WhatsAppSimulator.tsx`. Está montado como widget flotante y desplegable. Usa `useChatBot.ts` para manejar texto, grabación, transcripción, propuesta de acciones y confirmación.

Flujo típico:

El usuario escribe o dicta una frase.
Si es audio, el navegador lo captura con `MediaRecorder`.
`voiceModelService.ts` primero transcribe con Whisper y luego manda el texto a Llama para obtener JSON.
Si no hay credenciales o el modelo falla, se usa el parser local.
La propuesta se normaliza como `ParsedVoicePayload` y se muestra antes de confirmar.
Al confirmar, el store aplica los cambios y también persiste al backend con `POST /api/state/apply`.

5. Qué hace la IA y qué hace el parser

La IA tiene dos tareas distintas:

Whisper convierte audio a texto.
Llama convierte texto a un JSON de acciones.

El prompt de Llama vive en `src/services/voiceModelService.ts`. Allí se le pide una estructura concreta con `schemaVersion`, `intent`, `confidence`, `requiresConfirmation` y un array de `actions`. El código no confía ciegamente en la respuesta: `voiceParserService.ts` valida, normaliza y hace fallback si el JSON viene mal formado.

En otras palabras, la estructura la define el sistema, no el modelo. El modelo completa esa estructura y el parser decide si la salida sirve o si hay que degradar a reglas locales.

6. Reglas de negocio actuales

El parser reconoce y normaliza movimientos como:

alta de stock
reserva de stock
venta
deuda
pago recibido

También soporta frases compuestas. Si no encuentra un producto con suficiente confianza, el backend puede crear uno nuevo automáticamente.

Actualmente el modelo de producto incluye:

`name`, `productType`, `productModel`, `size`, `stockAvailable`, `stockReserved`, `price`

Eso permite separar prenda, modelo y talle en el ABM y en la interpretación de comandos.

7. Backend y webhook de Meta

El backend escucha por defecto en `3001` y expone:

- `GET /api/health`
- `GET /api/state`
- `POST /api/state/apply`
- `GET /api/meta-events`
- `GET /api/meta-webhook`
- `POST /api/meta-webhook`
- `GET /api/twilio-events` por compatibilidad histórica

El webhook de Meta verifica el challenge por GET y procesa mensajes por POST. Cuando entra un mensaje, el backend guarda evento, aplica acciones si existen y responde usando la API de Meta. También imprime un log de debug con la respuesta generada.

8. Persistencia y CRUD real

La persistencia local se maneja con `sql.js` y el archivo `server/data/erpvoice.sqlite`.

Hay CRUD real para productos:

- crear producto
- editar producto
- eliminar producto

El dashboard ya consume ese CRUD desde la solapa de ABM. Además, el backend puede hidratar el estado completo con `/api/state` y aplicar movimientos con `/api/state/apply`.

9. UI actual

El dashboard tiene estas vistas:

Resumen: inventario, cuentas corrientes y últimas transacciones.
Stock real: métricas agregadas de inventario.
ABM productos: alta, edición y eliminación real.
WhatsApp / Meta: eventos recibidos desde el webhook.

El simulador de WhatsApp ya no ocupa media pantalla: ahora es un widget flotante que se abre y se cierra desde un botón circular.

10. Arranque y comandos

Los scripts actuales son:

`npm run dev` - frontend solo.
`npm run dev:api` - backend solo.
`npm run dev:frontback` - frontend + backend.
`npm run dev:ngrok` - túnel aparte.
`npm run dev:all` - alias de `dev:frontback`.

La forma recomendada de trabajar es abrir dos terminales: una para `dev:frontback` y otra para `dev:ngrok`.

11. Riesgos y límites

El proyecto sigue siendo un prototipo. No hay autenticación, la persistencia es local y el estado se sincroniza por polling. Además, cualquier variable con prefijo `VITE_` se publica en el bundle del navegador, así que no debe usarse para secretos sensibles.

12. Lectura para tooling o IA

Puntos clave para otro modelo o agente:

El frontend transcribe con Whisper y estructura con Llama.
La estructura del JSON la define el sistema, no el modelo.
El backend es la fuente de verdad para la persistencia.
Meta es el canal principal actual; Twilio quedó como compatibilidad histórica en algunos nombres y endpoints.
El ABM de productos es real y opera sobre SQLite local.
